# 任务与数据恢复

先区分叙事任务、记忆整理和存储故障。浏览器断开不会自动取消后台 Workflow；重新进入故事后查看任务状态及 SSE 快照。不要因页面暂时没有新文字重复提交相同剧情。

## 任务恢复

| 症状                     | 查看位置                     | 当前恢复方式                                                                   |
| ------------------------ | ---------------------------- | ------------------------------------------------------------------------------ |
| 生成失败，草稿仍在       | `GET /api/v3/tasks/:id`      | 保留草稿；若 branch head 未变化，`POST /api/v3/tasks/:id/retry` 创建新 attempt |
| 已取消                   | 同上                         | 重新提交新 commandId；取消的 task 不能原地 retry                               |
| 提交版本冲突             | task error、当前 branch head | 刷新后重新提交，或从原输入前分叉；不要覆盖其他已提交回合                       |
| 正文已提交，记忆暂未出现 | `GET /api/v3/jobs`           | 等待 memory outbox；失败的非 generation job 使用 `POST /api/v3/jobs/:id/retry` |
| `MEMORY_BACKLOG`         | jobs 及上下文检查器          | 先让失败/积压的记忆整理完成，再重试；近期窗口不能覆盖的未整理事件不会被忽略    |
| 语义索引不可用           | 上下文 warnings              | 词法、关系和原文补尾仍工作；检查索引任务并恢复 Vectorize/AI binding            |
| `ENTITY_AMBIGUOUS`       | memory job error             | 明确人物 ID/别名或纠正原文后处理；系统不会随机合并同名人物                     |
| 原 PNG 不存在            | 资产 `hasPng`、PNG 导出 422  | 导出 JSON；提供原 PNG 后重新导入/补充，metadata 无法合成原画像                 |

生成重试创建新 task attempt；失败的非生成 job 重试加入新 `retryId`，从而获得新的 Workflow identity。旧尝试仍受 attempt、取消状态、来源与提交 fence 约束。不要直接把 D1 中 task 改成 completed，也不要把 outbox 强制完成来掩盖 cursor 缺口。

派发使用 D1 outbox 的持久状态与 **15 分钟 `dispatching` 租约**。每分钟 Cron，以及部分 API 的后台调用，都会尝试派发；恢复时间还取决于运行环境是否可用，15 分钟不是任务执行期限。

| 状态          | 调度行为与恢复边界                                                                                                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `pending`     | 先以 owner、payload 和状态 CAS 抢占为 `dispatching`，再调用 Workflow binding；一次调度最多取 40 项。并发调度器仅让抢占者派发。                                                                         |
| `dispatching` | Workflow ID 由 outbox ID 和 retryId 确定。若创建报错，先查同一 ID 是否已存在；创建成功而 D1 回执失败时保留租约。租约超过 15 分钟后退回 `pending`、返还这次派发计数，再按同一 ID 恢复，避免重复创建。   |
| `dispatched`  | 已确认 Workflow 存在，不因运行超过 15 分钟就重启。调度器查询较旧项的工作流状态；仍在运行或状态查询暂时失败时保留意图。工作流终止，或运行已完成却未留下所需 D1 完成状态时，标为 `failed` 供检查和重试。 |
| `failed`      | 确认创建失败最多自动派发 3 次；生成任务相应记录失败并保留草稿。非生成 job 可从 jobs 页面重试；来源 epoch 已变化的普通整理任务要求重建，cleanup/delete 仍可继续补偿。                                   |
| `completed`   | D1 已记录完成；生成 task 已完成或取消时，其旧 generation outbox 也可被调度器收尾。                                                                                                                     |

这些机制约束已提交剧情的幂等性，并不能保证外部模型调用或索引请求只发生一次。Workflow 的步骤重试及租约恢复以稳定业务 ID、D1 版本验证和可重复执行的清理操作处理迟到结果。

用同一个 commandId 重试同一 HTTP 提交是幂等重放；改变输入必须使用新 commandId。重新生成已提交回合先从其输入前创建分支，原分支保留原稿与记忆前缀。

## 纠正、遗忘和删除

作者纠正生成新原文及记忆 revision，并使旧结论的依赖失效。遗忘表示当前分支不再使用该项记忆，原文仍可留存。删除原文是更强操作：相关 source/spans、派生记忆、经验/能力证据、场景副本及旧任务副本被清理，其他分支也不能继续引用。

删除先在 D1 中执行 tombstone、来源失效、正文/派生记录擦除及 generation/epoch 变更，再由 cleanup outbox 补偿外部副本。清理包括相关 R2 任务产物、DO 流、embedding cache 和 Vectorize manifest；向量删除请求是异步的，后台 job 完成表示请求已成功执行，不代表索引传播立即结束。索引步骤也会检查写入后的有效性，对删除期间产生的迟到向量执行补偿。所有召回结果仍需从 D1 展开并验证版本、来源和知情范围，所以旧索引命中不能直接提供正文。

来源删除会保守清理该 owner 在删除之前创建的任务副本，不能把已擦除草稿当作可恢复正文。检查 `/api/v3/jobs`，重试 failed cleanup/index job 并重新确认来源无法展开；不要通过重新插入旧 source/embedding 绕过删除账本。仍有独立有效来源的派生记录可通过新的原文回放重新生成；被遗忘或删除的证据不能作为补偿来源。

## 备份范围

保存至少三类内容：D1 完整导出、R2 原对象及校验清单、部署版本与资源配置。D1 包含来源、事件、分支、授权、能力、procedure uses、游标及任务意图；只备份聊天正文无法完整恢复这些关系。R2 的 PNG 与任务产物也不能仅凭 D1 文件还原。

`GET /api/v3/branches/:id/export` 导出整个故事及其分支、事件、可见记忆、来源和 grants，用于用户归档；当前没有对应的完整故事 archive 导入 API。导出包括所有不可变记忆历史、lineage/水位、资料绑定和原始 JSON revision、能力/使用账本、实体、来源与证据及删除审计。PNG 以外部 R2 key 清单表示，不内嵌文件；它仍不是完整 D1/R2/DO 备份，不包含任务产物或 Workflow 运行状态。导出过程中剧情、投影或删除版本改变会返回 409，需要重新导出。Vectorize 是可重新生成的投影，但可用 `POST /api/v3/branches/:id/rebuild` 按已提交原文重建当前分支，输入包含 commandId 和 expectedHead；仍没有公开的一键全库重建接口。

重建会固定请求时的 branch head、owner epoch 和资料前缀，按 lineage 的可见原文逐回合回放，而不是复制父分支今天的记忆。可用且属于完整原回合的验证抽取产物会被复用；其他情况调用当前配置的抽取模型，因而不保证逐字恢复原来的摘要或推断。人物资料和知情来源按历史序号解析，分叉点后的父分支证据不参与；覆盖未来事件的观察及技能证据按子分支前缀重新整理。完成后再整理观察和语义索引。来源在回放期间被删除或纠正导致 epoch 改变时，回放停止，需要核对后创建新的重建请求。

重建是从合法证据重新产生投影，不是将数据库所有版本清空后重新安装。它不能还原已销毁原文、缺失 PNG、导出副本或尚未备份的 Workflow 状态，也不是无需人工检查的全库恢复工具。

旧版已完成的备份与本地资料恢复见 [迁移快照](migration-snapshot.md)。备份文件保存在仓库外的备份目录，未纳入 Git。用户的离线完整备份和应用中的删除是不同保存范围；恢复旧备份前应核对其时间和删除记录，防止重新导入后来删除的原文。

## 隔离恢复

1. 暂停向待恢复环境写入，记录 Worker 版本、各资源标识及最近完成的 outbox 状态。保留原环境和当前备份。
2. 在全新恢复用资源中校验 D1 导出和每个 R2 对象的 hash。旧 V2 SQL 用于旧版恢复；不能导入 V3 schema 或直接执行 V3 migrations。V3 恢复也需匹配对应代码与 migrations。
3. 使用同一批次的 D1 与 R2 备份恢复，再核对来源、revision、角色授权、分支头和 cursor。新的 DO 流由 D1 task 草稿重新读取；恢复时保留可检查的 task/outbox，不能假定旧 Workflow execution 会自动迁到新 binding。
4. 旧资料升级使用离线迁移脚本，只恢复卡片/世界书到全新 V3，详见 [迁移步骤](migration.md)。旧聊天仅归档；不要把自动记忆当作已验证 V3 记忆导入。
5. 本地执行 `npm run check` 和 `npm run test:e2e`，核对资料数、PNG 缺失、来源与分支隔离。独立远程预览已配置 Access，真实 Workers AI 生成及记忆链已完成一次 smoke；恢复环境仍须独立测试连接、生成、取消、记忆整理和来源清理，合成回放不替代这一步。

当前迁移 CLI 只允许回环目标，没有生产恢复或部署命令。2026-10-07 的远程预览恢复通过独立 D1 的受控操作完成，并在服务器内逐项比对 fingerprint 和 immutable revision，见 [远程记录](migration-preview-report.json)。该预览使用独立 V3 资源和 Access 保护，旧生产域名与旧资源没有切换。

生产切换是后续独立发布步骤：先核验目标代码、绑定、Access owner、资料版本和备份，再明确选择流量切换及回退方案。PR 合并、CI 成功或预览部署都不等于生产迁移完成；CI 只检查代码与本地环境，不执行存储恢复、部署或域名切换。不能把 V2 SQL 导入 V3，也不能把旧聊天/自动记忆当作已验证 V3 投影恢复。

## 输出超限与失败回合重试

模型输出上限同时用于正文和结构化剧情校验。推理模型可能将额度用于思考，即使正文很短，校验仍可能返回 `OUTPUT_TRUNCATED`；截断结果不得提交。输入组装为实际输出上限及安全余量预留空间，硬规则与证据放不下时明确失败。

调高输出上限后保存，再重试失败回合。每次显式重试从当前保存设置创建新尝试并冻结配置，运行期间的设置修改不会影响该尝试。旧尝试的 R2 快照保留；原始输入、分支版本、取消和并发提交约束继续生效。新尝试不继承旧尝试的正文，因此展示的草稿可能变化。

结构化校验会区分对白证据、标量值无依据和字符串值不匹配，并将多项错误的具体字段路径一起返回给修复请求。上次输出使用剩余输入预算保留，超过预算时明确标记截短，不再隐藏限制为固定 2048 token。普通叙事状态不能自动成为布尔/null世界事实：须采用有逐字客观证据的字符串值，或记录为经历；作者明确赋值才允许布尔/null。该提示改进不改变原有校验条件，也不接受截断、无来源或未获知的记忆。
